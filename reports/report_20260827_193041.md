### 🟡 MEDIUM

7. **Frontend trust surface** — every state-mutating request posts a Zod-shaped JSON body; the Edge Functions rely on `orderNumber+token` to authenticate. No JWT auth flow is visible for buyers (no signup, no email collection on checkout — only `name` + optional `phone`). All access control is per-order token, stored in `localStorage` under `shopee_orders_v1`. If a customer clears storage they lose access; the operator has no recovery path other than the order ID+token pair. The replacement page's "auto-fill from localStorage" feature means a shared-device XSS / browser-spy attack would leak every recent buyer's order token.

8. **Support chat is an in-app live channel** — the `support/:topic/:token` page uses an Edge Function with `image_base64` uploads and 3-second polling. The chat schema has `sender` (`user`|`support`) and `seen_at` fields — but `token` is the only auth. Brute-forcing chat tokens would expose customer-to-support conversations.

9. **WAF/CDN posture is partial** — Cloudflare is fronting the site but the origin (`shopeelabs.lovable.app`) is publicly addressable. Security headers: only `Strict-Transport-Security` and `X-Content-Type-Options` are set; **no `Content-Security-Policy`**, no `X-Frame-Options`, no `X-XSS-Protection`. The site is clickjackable and inline-script-injectable through any future XSS in the support chat (which accepts `image_base64`).

10. **`robots.txt` discloses internal structure** — `Disallow: /admin /checkout /cart /orders/` confirms an admin panel exists, but `/admin` returns the SPA loader with no auth. The "admin" route exists in the TanStack router manifest (no separate `admin-*.js` bundle was found, suggesting it's loaded from the same main bundle as the rest, possibly gated by an in-app role check we can't see without an active session).
